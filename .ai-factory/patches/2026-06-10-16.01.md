# Polling worker stale runtime state

**Date:** 2026-06-10 16:01
**Files:** polling.php, services/TelegramBotRuntime.php, services/TelegramBotRuntimeFactory.php, services/TelegramUpdateDispatcher.php
**Severity:** high

## Problem

Polling worker kept long-lived runtime state after switching Telegram handling from webhook to getUpdates. A worker started before midnight would continue using the old date for callback folders. Changes to bot-data after `/cache/clear` would not affect menus until the polling process restarted.

## Root Cause

The webhook implementation had short-lived request state: every incoming webhook request rebuilt dependencies and used the current date. The polling implementation reused one `TelegramBotRuntime` indefinitely, but that runtime contained values that are only safe for a single request/update:

- `DateTimeImmutable $currentDate`
- `TelegramBotApi` built from a snapshot of firms/address data

This converted request-scoped data into process-scoped data.

## Solution

- Removed `currentDate` from `TelegramBotRuntime`.
- `TelegramUpdateDispatcher` now creates a fresh `DateTimeImmutable('now', Europe/Moscow)` for each callback update and ensures the current-day Yandex Disk folder exists before dispatching `CallbackQuery`.
- `polling.php` now keeps a lightweight Telegram client for `getUpdates`, but creates a fresh full runtime for each received update. That refreshes cached/backend bot-data without requiring worker restart.
- Added `[FIX]` log entries around polling startup, connection, and update processing with refreshed runtime.

## Prevention

- In long-running workers, do not store request-scoped values such as current dates, cache snapshots, or mutable configuration in process-scoped runtime objects.
- During review, check every value moved from webhook/request flow into polling/daemon flow and classify it as process-safe or update-scoped.
- Regression coverage should simulate a worker that processes callbacks across a date boundary and after bot-data cache invalidation.
